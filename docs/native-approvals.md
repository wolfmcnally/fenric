# Native approval integration walkthrough

Fenric is a standalone dialog tool and an independently usable request-bound renderer. It neither installs nor requires another approval product. This guide describes existing interfaces and a host integration transaction; it is not a turn-key native host, hook installer, credential broker or production admission factory. See [Python API](api.md), [exact wire/mappings](integration.md) and [security](security.md).

## First distinguish the question

A script can use confirm and inspect ok/True versus ok/False for its own bounded question. That does not override a coding harness's pending permission request. Native approval requires the supported owner of the exact original callback/RPC, with the original action, thread/session/request and transport generation retained. A translated owner reply is attributed delegate evidence, not a forged renderer observation or owner cryptographic signature. Its receiving application must explicitly admit the delegate's mandate/scope and independently retain the original proposal, authenticated reply and qualifications; Fenric does not mint that mandate. Mandatory platform/native confirmation floors remain authoritative.

## Worked host transaction

For an exact supported command/tool approval already intercepted by a trusted application:

1. The native owner retains the original pending callback and complete action, including optional-field presence, actual offered ordered choices and native IDs. It checks current custody and policy; unsupported fields/modes refuse without pruning.
2. The host independently admits its renderer process/private endpoint and current principal map. It prepares a closed Request with complete DecisionContext, canonical decision digest, nonce, immutable wall expiry and separate TransportBinding. Native action digest and renderer decision digest are different domains: join them explicitly, never compare unlike digests as if they were identical.
3. The trusted host passes the inherited connected Unix endpoint to Fenric. Only after that independent bootstrap is the existing call meaningful:

```text
result = fenric.run_integrated(admitted_channel)
```

admitted_channel here names the host's existing admitted connected socket; this line is interface notation, not a runnable factory. The CLI equivalent is interact --channel-fd N for an already inherited descriptor. A worker-created socket or descriptor integer grants nothing. The host closes its original socket after this one-shot call; Fenric shuts down the connection and closes its duplicate.

4. Fenric derives the exact presentation from the original request and checks actual winning-surface observations. Remote uses the verified protected proxy login; local process UID is account evidence only. An unadmitted local surface is review-only. A private protected relay may deliver availability under separately authorized capability handling; missing relay is unavailable, never permission to publish bearer URLs in ordinary model/chat/bus history.
5. A valid submitted response is correlated to original interaction, nonce/digest, response schema, host/session/worker/generation, principal and both deadlines. Cancel/expiry/supersession/error never become allow. The host rechecks current principal policy, revocation and still-pending native custody, then consumes one-use proof before its supported callback.
6. The host reports receipt and native delivery separately. A callback return/submission is not action completion; verify the original native tool result and intended effect/absence independently. Unknown/submission-unproved remains unknown. Competing resolution, reconnect or restart does not authorize replay, and completed effects cannot be undone by later cancellation.

The executable isolated socket examples and refusal cases live in the source archive's tests/test_interaction.py, with closed golden frames under tests/fixtures/operator-response/. They substitute a renderer/host and do not contact native sessions or prove a real person's consent. They are the worked protocol fixture, not a production runner.

## Claude: two different contracts

The integrated claude.approval mapping requires its complete tool input and exact native tool-use binding. It does not discover an existing daemon or install a hook. claude.question is a supported structured SDK question mapping, not proof of a standard daemon question bridge.

Separately, operator-reported qualification as of 2026-10-16 records authenticated phone Allow once, Deny and phone Cancel in disposable standard daemon-managed Claude Write tests on two macOS hosts through scratch-local PermissionRequest hooks. These operational observations are not reproduced by this archive’s synthetic tests. Those hooks bound the still-live invocation, original session/tool/input and a one-use nonce/context; PermissionRequest input did not supply a tool-use ID. Their wrapper returned the supported hook decision to that same pending invocation. It did not fabricate a missing tool-use ID or claim to use the different integrated claude.approval shape unchanged. The fixture is separate test application source, not a packaged Fenric installer or universal deployed bridge. This evidence does not qualify retroactive capture of open requests, other tools/projects, auto-mode permission bypass or global hook installation.

### Opt-in Bash callback example (source archive only)

As of 2026-10-19, the installed CLI was observed as Claude Code 2.1.303. The current [official hooks reference](https://code.claude.com/docs/en/hooks) was retrieved 2026-10-19; it is a mutable, unversioned reference, not proof that this installed binary implements every current detail. No redistribution permission was established, so this guide links it rather than mirroring it. Its relevant native decision fields are behavior, updatedInput, updatedPermissions, message and interrupt. The example emits only behavior (plus a fixed denial message and interrupt), never input or permission amendments. The documented event names are PermissionRequest, PreToolUse and PermissionDenied; a fresh callback is different from an already-denied notification.

The source archive includes [claude_permission_hook.py](examples/claude_permission_hook.py). This is an opt-in, one-command example, not a hook installer, universal Claude adapter or new Fenric CLI verb. It admits only the fixed stdout-only printf demonstration declared by its TEST_COMMAND constant. It does not execute that command. Its own native callback remains pending while Fenric collects; a prepared allow response does not prove Claude consumed it or ran the command.

An operator-approved private scope file supplies session_id, cwd, permission_mode, the complete exact tool_input object (command and optional string description only; sandbox overrides and other fields refuse), host_label, immutable expires_at_ms, relay_approved, an absolute relay_command argument array and expected_remote_login. The cwd must match the physical path reported in native hook input, and its admitted temporary root is tempfile.gettempdir() in the hook process environment. The scratch cwd must be a direct nonsymlink child of that system Python temporary directory with the fenric-native-bash-test- prefix. The mode string must match the actual native hook input; verify the effective manual mode at activation rather than guessing a string. No example scope or enabled hook is installed by this archive. Validate the complete relay/account scope before spending the one-use claim. Receipts use fixed value-free refusal labels (such as cwd, clock, surface, identity and relay); no raw paths, inputs, parser messages or URLs are diagnostics.

After separate approval and exact scope preparation, invoke the example with the selected Fenric environment's Python and the scope filename as its sole argument, with native hook JSON on stdin. It accepts only PreToolUse and PermissionRequest for the admitted Bash input. A valid unsupported event exits 4 with no stdout, no collection and no retry. Malformed input or internal failure cannot grant. Do not put tokens, secret values or arbitrary service-exposure commands in the scope.

The separately approved local hook entries must use matcher Bash and an explicit timeout of 930 seconds, covering the maximum 900-second immutable interaction plus identity/relay/cleanup budget. Verify the installed hook failure policy before activation; do not rely on the documented default timeout. This example's PreToolUse asks only on the exact admitted input and denies other Bash inputs. PermissionRequest Deny, Cancel and internal failures return deny with interrupt=true, halting that scratch turn. An existing native prompt or another supported host callback can settle first; the first decision wins. Never retry a spent claim, infer callback consumption from the receipt, or extend the original expiry.

Phone collection uses the existing protected Tailscale configuration and native GUI; it refuses a local winning surface or changed account identity. Its source observation is version-bound to the existing Session implementation, not a public provenance API. An early URL is only availability, and a generic standalone confirmation is not native permission. A missing GUI, protected relay or exact pending callback is unavailable. The example cannot reverse an auto-mode classifier denial. PermissionDenied retry is not a native allow response, and sandbox network-request prompts do not supply this PermissionRequest callback. Use the receiving harness's supported native permission controls when that callback is absent; enabling a different hook or permission mode is a separate operator decision.

The owning tests exercise actual Session settlement with synthetic remote observations, exact callback output, one-use custody, both clocks and refusal behavior without a native window or service. As of 2026-10-19, a separately approved disposable manual-mode Bash test also verified authenticated phone Allow through the original PermissionRequest callback and the actual fixed-command stdout once, followed by native stop and scratch-hook cleanup. That bounded observation is reusable callback evidence, not universal hook installation, auto-mode support or proof that this reusable handler is deployed. Production hooks remain unconfigured.

## Reusable manual Bash permission helper

The package module `fenric.claude_permission` provides an opt-in system-wide handler for native Claude PermissionRequest Bash callbacks. It has no project-directory filter: each original native cwd, session and complete tool input stay bound to that invocation. Only native mode `default` (the observed Manual mode) is handled. Other modes, tools, unsupported input (including events over the 64 KiB bound or an unexpected native tool_use_id) and already-denied notifications leave the native controls in force; this helper cannot reverse auto-mode classifier denials. It never executes the Bash command, rewrites its input, applies suggestions or grants session/rule permissions.

Each callback gets a fresh request identifier and independent real Session, with an immutable wall-clock and monotonic lifetime of at most 900 seconds measured before configuration/identity work. The existing protected remote account and winning remote surface are checked again before returning an allow. Ordinary questions remain unchanged. A selected control, early URL, relay acknowledgement or prepared callback does not prove human submission, native consumption or command completion. The helper owns only its inherited pending callback, not retroactive capture or cross-process deduplication of an invocation ID the native event does not supply.

Configuration is a private owner-held regular JSON file (no group/other permissions), passed as the only argument. Its closed fields are:

```json
{"schema":"fenric.claude-permission.v1","host_label":"Receiving Mac","expected_remote_login":"operator@example.invalid","relay_command":["/absolute/operator-notifier"]}
```

The label is displayed, the account must match the existing receiving node's configured protected identity, and the executable argv receives one JSON availability object on stdin. The relay is required for this phone-only helper to deliver a link; its implementation is external and operator-selected. No particular transport product, its identity/key model, executable or service is mandatory to Fenric. Optional external glue may connect independent tools; it must establish any sender authority itself. `native_session_id` is correlation metadata, never a signing mandate. Keep the protected link inside the authorized delivery route.

The notification contract is exactly schema `fenric.permission-availability.v1`, status `available`, request_id, native_session_id, host_label, expires_at_ms and url. Command, complete input and cwd are shown in the approval UI and excluded from the announcement. The relay runs once, without a shell or cwd/ancestry change, with stdout/stderr discarded and a ten-second timeout. At least 600 seconds must remain at handoff; the delivery glue must also check remaining time when publishing. Success means the program accepted the notification, not human or device receipt. There is no automatic retry after uncertainty. Existing ordinary remote `announce` must be empty for this integration to prevent duplicate capability disclosure; the helper never changes it.

An authenticated remote Allow returns exactly one native one-action allow. Remote Deny or Cancel, expiry, parent loss, account drift and uncertain relay failure return deny with `interrupt:true`, stopping that declined or uncertain turn rather than inviting a repeated prompt. A local answer/close does not authenticate remote consent: it returns no decision so the native prompt can proceed. Configuration/account/remote/render unavailability and insufficient remaining time before link handoff also return no decision rather than making an infrastructure failure a system-wide Bash veto. These exit-0 empty-stdout paths grant nothing. Malformed native JSON exits 4; with the required `onFailure:"block"`, a helper failure or hook timeout is harness-denied rather than a fallback. Native policy and any earlier supported decision remain authoritative. An input-shape change deactivates this version-bound helper with the fixed unavailable stderr line; verify the receiving CLI before activation. The documented failure-policy claims are from the mutable official reference linked above; the observed live Bash proof establishes default-mode Allow/continuation only, not an observed timeout or interrupt-denial test.

For an installed package use the selected environment's isolated module invocation, `python -I -B -m fenric.claude_permission CONFIG`. An approved direct-file deployment may instead use that environment's `python -I -B /absolute/qualified/claude_permission.py CONFIG`; isolated imports then come from that interpreter's installed Fenric, so its actual engine/session/remote bytes must be checked against the rollout record. Do not assume a version label establishes internal marker compatibility. The direct-file and module forms are covered by offline entrypoint checks; actual receiving-host GUI/account/relay qualification is separate.

Global activation is an explicit operator action, not performed by importing/installing this module. The unactivated proposal appends one global PermissionRequest group matching Bash, containing one command hook with timeout 930 and onFailure block. Preserve all existing entries/order; inspect applicable project/local settings and remove or disable only separately approved duplicate handlers, never run both global and project copies. There is no demonstration PreToolUse force-ask guard. Each receiving host requires its own local executable/account/GUI/relay and duplicate-hook inventory. Existing sessions may need a supported settings reload or restart; do not stop unrelated work or promise automatic cold recovery.

Before activation, retain the exact settings backup/hash, helper/config/runtime identities and added hook object. Rollback removes only that exact added object and its dedicated integration config after checking for concurrent edits; restore a whole backup only when unchanged unrelated settings are proved. Keep native controls and existing user data. A first normal requested Bash permission after separately approved activation is real-use acceptance; no further fixed-line demonstration is required. Concurrent unavailable surfaces fall back to native controls; no broker or recovery framework is added.

## Codex: exact supported subset, live gap

The renderer supports the documented 0.163 command subset, retaining complete original RPC, optional presence/nulls and ordered one-action choices. Recognized session-wide and execution-policy alternatives and well-formed proposed rules remain inspectable in the complete original, but only actually offered one-action accept/decline/cancel answers can be returned. Session/rule answers, network authority, permission objects and stdin/subcommand approval IDs refuse. The native owner must own the original app-server request/connection; generic user-role text is not an equivalent callback. Automated command and external host/relay fixtures establish source consistency only. As of 2026-10-17, live Codex phone approval remains unvalidated, including host bootstrap, actual pending callback eligibility, authenticated publication/response, one-time native settlement and effect readback. An ordinary command may execute without asking; do not force an escalation or failure merely to create a demonstration without explicit authority.

### MCP tool-call confirmation

This mapping corresponds to the root-thread requestUserInput path used when the native ToolCallMcpElicitation feature is not enabled; it does not enable, disable or replace that feature.

For the pinned 0.163 MCP confirmation subset, the host supplies complete original `{rpc,action}` through `codex.question`, not a reconstructed action inferred from question prose. The in-progress native MCP item, RPC item ID and prefixed question ID must join exactly. Fenric displays server/tool/arguments as untrusted action data and returns only the keyed Allow or Cancel actually offered. A session alternative remains inspectable but nonselectable; persistent-choice variants refuse entirely. Ordinary structured questions remain a separate mapping. See the [MCP subset reference](integration.md#native-mcp-confirmation-subset) for exact fields and representability limits.

The owning host must translate that exact keyed selection to the vendor reply for the still-pending original native request; it must never emit a session/persistent choice, recreate an item from prose or treat a generic answer as authority to invoke an MCP tool directly. The isolated producer/socket fixtures cover display, response validation, joins and refusal. As of 2026-10-17, this new mapping has no claimed live native phone qualification or installed host bootstrap. Installation, actual child tool selection/check-in, principal/callback custody, protected delivery and observed tool continuation remain separate adoption/acceptance steps.

## What is still separate setup or acceptance

Current principal/delegate admission, native-owner bootstrap, protected delivery sink and host-specific lifecycle recovery must each be qualified. No source example grants credentials, installs hooks, changes authentication or exposes network services. Installation and command availability do not establish these relationships. A production host application/installer is future integration work if absent; document the exact missing capability rather than substitute a synthetic answer. Linux/Windows GUI and host routes are unverified. Cold-start automatic recovery and queued messaging require their own observed acceptance. Follow [troubleshooting](troubleshooting.md) when a supported route is unavailable.
