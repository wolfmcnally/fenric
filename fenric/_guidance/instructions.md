## Fenric — direct user interaction

When the operator selects a coordinator for project questions, choices and action confirmations, use Fenric rather than a worker-only native question tool, including when an older project skill defaults to one. Retain the complete proposal and expected choices, start one tracked invocation, and promptly send its live protected URL, minimal question label and caller-owned lifetime bound through the caller's own existing authorized delivery channel to that operator-selected coordinator. The coordinator presents it in the operator's chosen conversation even when a local dialog opens. Keep sensitive draft contents out of the relay. Ordinary questions do not automatically use a separately configured native-permission relay; never borrow an identity, credential or signing route.

The originating caller collects and validates the terminal result of that same invocation against the unchanged proposal and current scope. URL delivery or chat acknowledgment is not an answer. Decline, cancellation, expiry, missing or uncertain results grant nothing. Respect operator availability rules and avoid duplicate dialogs. Under this configured workflow, missing Fenric or a supported live URL handoff is a blocker to report to the coordinator, not permission to silently substitute a worker-only question. Diagnose and refine failures. Mandatory native security prompts remain separate: this workflow cannot settle an existing native callback, reverse a denial, widen permissions or authorize an already-blocked action. Fenric remains usable without a coordinator or any particular messaging product; delivery is optional operator-configured integration, not a package dependency.

Prefer Fenric for all user-requested and user-required responses whenever this host supports the appropriate surface: presenting answers/explanations, asking questions, collecting input, choices, reviews, decisions and confirmations. This preference adds no approval gate to ordinary responses or already-authorized work. Acknowledging information is not approving an action. Follow the operator's existing availability and interaction rules; do not open duplicate dialogs. If a required surface is unavailable, state the actual blocker and use an already authorized supported fallback without claiming authentication or native success.

Use the installed `fenric --help` and the verb's `--help`. Present information with `fenric notify --message "The requested result"` or sanitized rich content with `fenric custom --html-file response.html`. Ask a bounded yes/no question with `fenric confirm --message "Proceed with the described action?"`; inspect true versus false, not merely exit 0. Use `fenric ask --question "What should change?"`, repeating the question option for more fields; `fenric pick --message "Choose a scope" --option local --option remote`; or `fenric form --spec-file form.json`. Prefer a wizard for several substantial decisions so the user reviews one question at a time; choose the layout explicitly, since question count never switches it automatically. There is no wizard verb: `fenric --spec-file questions.json` accepts an ask spec with `"presentation":"wizard"`, stable question IDs, branching and final review. These examples authorize no named action.

Use `fenric ask --gallery-file manifest.json` for supported local PNG comments. Charts require caller-prepared code/data and an already provisioned toolchain; setup is not implied. Collect secrets only through the masked secret surface directly into an explicitly authorized supported file, for example `fenric secret --field API_KEY --into .env`; never pass or read values through model/chat/logs, ordinary questions or command arguments. Verify the receiving host and destination and inspect status/filled metadata, never secret contents.

Standalone exit 0 means answered; inspect the validated JSON or status. Exit 2 is cancelled, 3 invalid/error, 4 unavailable/expired. An early URL/status is availability, not an answer. A selected control or screenshot does not prove submission. Missing, cancelled, failed, superseded or expired results are not consent. A standalone result validates shape; it does not attest authenticated operator origin or resolve a native permission request.

For authoritative responses, use an already qualified host-owned private channel and trusted renderer. Validate the actual renderer-observed authentication basis, subject, receiving node, surface and session against the host's current principal policy, exactly; null is not a wildcard. Remote account evidence comes from the protected route's server-verified Tailscale proxy login, never browser JSON. Local process UID is account evidence, not proof of physical interaction; a tailnet account does not identify a particular phone or person. URL possession, a copied/forwarded claim or a coordinator signature alone is not consent.

Bind the complete original interaction/question/action, nonce/digest, native request/session/worker/host identities, transport generation and admitted response schema to the still-pending request. Preserve exact action scope and optional-field presence. Check valid submitted terminal response, immutable wall-clock expiry and monotonic lifetime before consuming the one-use proof; reject stale/replayed/mismatched or competing/superseded requests. Recheck principal policy and pending custody when consuming. Collection, correlated receipt, native callback delivery and actual action effect are separate; unknown or submission-unproved stays unknown.

Settle native permissions only through the original request's supported, qualified native bridge/callback, retaining native denial, sandbox, network and scope restrictions. `fenric interact --channel-fd N` consumes an already admitted inherited private Unix socket; the flag creates no authority. Generic Fenric answers never bypass harness policy, rewrite tool input, create grants or configure hooks. Guidance presence does not qualify a native adapter on this host. Check current host-specific qualification evidence; automated/schema tests alone do not prove a live Claude or Codex phone approval loop. Missing qualification is a blocker to that route, not permission to install, alter identity/authentication/settings/network, or add an approval gate to unrelated work.

Run `fenric guidance read` for the installed agent usage guide: supported review/comment recipes, result handling and standalone versus native boundaries. It is read-only and does not apply instruction changes. Consult the source documentation for the full command/spec and request-bound integration contracts. Recheck host GUI and already authorized phone-route prerequisites rather than assuming another machine's setup.
